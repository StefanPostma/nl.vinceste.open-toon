# ADR-0006: ToonWater opt-in mechanism (setting, runtime capabilities, migration default, races, detection)

* Status: accepted (2026-11-12); **rev 3 (2026-11-13, review finding C-02)**: an answer that is being written to the tile (the status write is a round trip to Homey) when the user switches the feature off is dropped, and the warning that may have landed meanwhile is taken back, so the warning is gone in every exit path (FR-55 AC2); a switch off that fails restores the state so that the next answer shows itself again; **revised rev 2 (2026-11-12)** after the design reviews: hint and disable message amended (Insights clause, amends FR-59 wording), warning slot limited to feature flags, probe budget and priority, compensating removal on a failed enable, options set only when they differ, water back-off escalation for non-404 failures, `html-200` classification, `planSettingsChange(newSettings, changedKeys)`. The migration-decided cases moved to ADR-0018. Revision log: `docs/sdlc/archive/05b-design-revision-log.md`
* Related: `05-architecture.md` §6; FR-50..62; `01` D-1..D-6; `04` §7, M-1..M-7, R-01..R-06, R-36; HS-21, HS-25, HS-30, HS-31, HS-37; ADR-0007 (cards), ADR-0010 (migration), ADR-0017 (contract exception), ADR-0018 (migration-decided devices); reviews compat issues 3, 8, 9; robustness R-03, R-13, R-16, R-23, R-24; standards F-06, F-10

## Context

Since PR #21 (`f705a70`) every device carries `measure_water`, `meter_water.today`, `meter_water.total` (`app.json:102-104`) and polls `/water.html` even without the add-on (404 on every update, `device.js:173-190`). Devices paired before PR #21 never received the capabilities and raise `Invalid Capability` (`device.js:33-38` migrates only `alarm_water.hotwater`). The owner wants ToonWater as a per-device opt-in: off = no capabilities, no polling, no 404 noise, no water cards; on = all of them; existing users lose nothing. `alarm_water.hotwater`, `hotwater_dispensing` and `alarm_water_changed` come from `burnerInfo` (`device.js:475-477`) and are **not** ToonWater (04 R-36). Homey: `setSettings` does not call `onSettings`; `removeCapability` breaks dependent Flows and may delete the Homey-side Insights history of the removed logs (`04` U5, HW-08); `addCapability`/`removeCapability`/`setCapabilityOptions` are expensive and must be guarded; `onSettings` returns `Promise<string|void>` and Homey shows the toast only after it settles.

## Decision

1. **Feature object** `lib/features/toonwater.js` (the only file naming `/water.html`): `setting: 'toonwater_enabled'`, `statusSetting: 'toonwater_status'`, the three capabilities, `legacyIf(caps)` = any of the three present, one poll group `water` (`critical:false`, `absentOn404: {backoffMs: 15 min}`, `failBackoffMs: 5 min`, `failEscalateAfter: 3`, `escalatedBackoffMs: 15 min`), `probe`, `probeBudgetMs: 3000`, `pairCheckbox: 'when_detected'`, guarded cards `update_water` (`onDisabled: 'reject'`, overridden for migration-decided devices by ADR-0018), trigger `measure_water_changed`, rule for it, `hintAfter404Ms` 24 h, `warnWhenMigrationDecided: false` (ADR-0018). Provenance header: interface from `03` §5.3 + this repo's GPL-3.0 PR #21; nothing from `oepi-loepi/*`.
2. **Setting/UX**: checkbox `toonwater_enabled` (`value:false`) and read-only label `toonwater_status` in group "ToonWater (optional add-on)", texts from FR-59 (en + nl) with **one amendment** (FR-59 allows only semantically equal polishing, so this ADR records it): the hint's last sentence and the "disabled" save message name the Insights risk until HW-08 (`04`) / HW-06 (`01`) settles U5. Hint, en: "... Turning it off removes them again; Flows that use them will break and their Insights history may be lost. After turning it back on, check those Flows." nl: "... Uitzetten verwijdert ze weer; Flows die ze gebruiken gaan kapot en hun Insights-geschiedenis kan verloren gaan. Controleer die Flows na het opnieuw inschakelen." Disabled message, en: "ToonWater turned off. The water items were removed; Flows that used them need to be updated and their Insights history may be lost." nl: "ToonWater is uitgezet. De wateronderdelen zijn verwijderd; Flows die ze gebruikten moeten worden aangepast en hun Insights-geschiedenis kan verloren gaan." The same sentence goes into the README section "what happens to my Flows" (FR-122). If hardware shows the history survives, the clause is dropped (text-only change). Status written with `setSettings` on transition only; after an `onSettings` save the computed status is re-asserted once via `this.homey.setTimeout(0)` guarded by `_stopped` (Homey may persist the `newSettings` snapshot after the save; HW-13). Save messages returned from `onSettings`. `setWarning` while enabled and 404 under the ADR-0018 rule; cleared on first valid payload, disable, delete and every init while off. **The warning slot knows feature flags only** (`toonwater_not_found`, future features); a missing address is `setUnavailable(__('address_missing'))` and never a warning (HS-25: unavailable blocks actions, which is right for an unconfigured device; `setAvailable()` does not clear warnings, so mixing the two would leave stale warnings).
3. **New devices**: off unless the pairing checkbox (shown only when the pairing probe returned `detected`) is ticked; `buildNewDevice` passes `settings.toonwater_enabled`, an explicit `capabilities` list, `capabilitiesOptions` for the trio when ticked (HS-34 pairing override) and `store: {migrationVersion: 1, toonwaterDecidedBy: 'user'}`.
4. **Existing devices**: decided once, from the capability list only, gated by the absent store marker; none of the three -> `false`, nothing added; all three -> `true`, nothing changed; some -> `true`, missing ones added. Never from the setting default, never from the network, never removes. Persisted with `setSettings` together with `store.toonwaterDecidedBy = 'migration'` (ADR-0018); the migration reconciles capabilities itself. A user's later "off" is never flipped back.
5. **Toggle, serialised** through the device's promise queue; `onSettings` uses `planSettingsChange(newSettings, changedKeys)`: it acts only on keys in `changedKeys`, normalises before comparing (so a `poll_interval` saved as a string or an address with extra whitespace does not bump `gen`), and returns `{errors, addressChanged, startPoller, intervalChanged, toggles[]}`; `startPoller` is true when the stored address was invalid (`0.0.0.0`/empty) and the new one is valid, and the poller's first success calls `setAvailable()`. **Off->On**: `featureGen++`; `addCapability` x3 guarded, **wrapped**: if one of them throws, the ids added in this same step are removed again (guarded) and the error is rethrown, so `onSettings` rejects, Homey keeps `false`, and no stray water capability is left behind; then options reconciliation: `setCapabilityOptions(id, opts)` **only when** `getCapabilityOptions(id)` deep-differs from `driver.manifest.capabilitiesOptions[id]` (C-CAP-4 kept, three expensive calls skipped in the common case); then `probe` with **`kind: 'write'` priority and a 3 s budget** (the same budget pairing uses), so the network part of `onSettings` is <= 5 s (one in-flight request settling) + 3 s = 8 s worst case and typically well under 1 s; a probe cancelled by teardown/address change classifies as `unreachable`; status + message (404 keeps the capabilities, D-4); `refreshSoon(['water'], 0)` is scheduled, not awaited. **On->Off**: `featureGen++` **first** (the in-flight water request, if any, is not aborted; its response carries the old gen and is dropped before `hasCapability` is consulted), `removeCapability` x3 guarded, `unsetWarning`, status Off, delete `store.waterFirst404At`, write `store.toonwaterDecidedBy = 'user'`, return the amended "turned off" message. Every step re-checks `_stopped` before a Homey call. Rapid tick/untick/tick resolves to the last save; address change is processed before toggles and re-probes an enabled feature.
6. **Detection**: 200 + `result:"ok"` + object `water` = `detected`; HTTP 404 = `not_found` (03 T8, M confidence); timeout/refused = `unreachable` (availability stays with the thermostat); other 200, 403, 500 = `unexpected`/`http` (a flat `waterflow`/`waterquantity` payload gets the "this is the sensor module's address" hint). **Back-off**: a 404 backs off 15 min at once; any other non-success water result backs off 5 min for the first three consecutive failures and 15 min from the fourth on (`failEscalateAfter: 3`), status text per kind, so a Toon whose web server answers 200+HTML, 403 or 500 for a missing page costs <= 100 `/water.html` requests per 24 h instead of ~288, and HW-07 can change wording but not load. FR-55 AC4's bound is 97 for 404 and 100 for the other kinds (both asserted). The mock has water modes `404`, `html-200`, `403`, `500`, `junk`, `slow`; if HW-07 shows that a missing add-on answers 200 + `text/html`, `probe` maps `unexpected` with `text/html` to `not_found` (one line). Persistent failure: one info line on entry/exit, never error level, never auto-off.
7. **FR-62**: one timeline notification after 24 h of continuous 404 for a device enabled **by migration**, restart-safe via `store.waterFirst404At` and `store.waterHintSent` (details, including `createNotification` failure handling, in ADR-0018).

## Consequences

* P1 users (no add-on, device paired since PR #21) keep their empty water tiles until they untick the box and are told once where to do that (FR-62); nothing is ever removed by an update.
* Disabling is the only `removeCapability` in the app; its consequences for Flows **and Insights history** are stated in the hint, the save message and the README (ADR-0007, `04` R-04).
* A failed enable leaves the device exactly as before the save (compensating removal); a save never blocks on a queued cycle (write priority, 3 s probe).
* Hardware items: real status for a missing `/water.html` (HW-07), `label` refresh via `setSettings` and merge-vs-overwrite of a poller `setSettings` during a save (HW-13), options after `addCapability` and for a present-but-unlisted capability (HW-03), Insights after remove/re-add (HW-08 of 04), save duration with ToonWater enabled on a slow Toon (HW-13).
* Rejected: probe-then-remove at upgrade (04 §7.4 first draft; the only place an update would remove capabilities); refusing to save on 404 (dead end for a fresh add-on that has not written its page yet); a "hide only" mode (parked, D-6); `setCapabilityOptions` unconditionally after every add (three expensive calls inside the save for nothing in the common case); ranking `address_missing` in the warning slot (two mechanisms for one condition).
