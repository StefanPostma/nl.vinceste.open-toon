# ADR-0014: `vacation` enum value, `burner_state` capability, plain `meter_power` policy, meter precision and discovery

* Status: accepted (2026-11-12); settles OQ-07 (vacation), OQ-11 (ids), OQ-05 partially; **revised rev 2 (2026-11-12)** after the design reviews: plain `meter_power` frozen (never written), counter-decrease policy replaces the blanket monotonic guard (amends the reading of `04` B-8), `burner_state` compose definition fixed (`uiComponent: sensor`, `setable: false`, `insights: false`), the `vacation` picker UX recorded, setpoint rounded to the capability step. Revision log: `docs/sdlc/archive/05b-design-revision-log.md`
* Related: `05-architecture.md` §14; FR-10, FR-12, FR-20..22, FR-28, FR-30..32, FR-114; `04` §4.3, C-CAP-3, C-CAP-6, B-8, B-9, R-19, R-20, R-22, R-25; `03` I2, I3, I6, §4.4; HS-33; reviews compat issue 7, robustness R-05, R-18, standards F-07

## Context

`TEMPERATURE_STATES` (`device.js:7-13`) has no value for `activeState` 4, so a Toon in holiday mode sets `temperature_state` to `undefined` (`device.js:472`). `burnerInfo` is already read with the temperature (`device.js:475-477`; `2` = hot water in code; `1` = heating per issue #26; `0`/`3` per 03 I2). Every power update writes the undeclared `meter_power` from `(dayUsage + dayLowUsage) / 1000` (`device.js:374-378`): *today's* consumption, which resets at midnight, into a cumulative capability on a driver with `energy.cumulative: true`; era-0 devices still own a plain `meter_power`; two independent samples say the HTTP `GetCurrentUsage` answer has no `dayUsage`/`dayLowUsage` (03 I6). Gas and kWh are truncated to integers (`device.js:384,398,442`). Meter nodes are hard-coded `dev_2.x` (`:332-341`), wrong for the `dev_3` generation and for users with `dev_4.x` (#9, #10). A Toon can hold setpoints such as 1975 set by other clients (03 I3), off the capability's 0.5 step (`app.json:111-115`). `capabilities.md` lists `uiComponent` among custom-capability properties and allows `sensor` for `enum`; a getable-only enum without it renders as a picker (HS-33). Legitimate counter decreases exist: smart-meter replacement, P1/M-Bus adapter re-pair on the Toon, a ToonWater total preset (`/setnew`, 03 §5.5), a Toon reset.

## Decision

* **Vacation**: additive enum value `vacation` ("Vacation"/"Vakantie") for `activeState` 4 in `.homeycompose/capabilities/temperature_state.json`; read-only: offered in `temperature_state_is`, not in `set_temperature_state`; the capability listener rejects it with `__('error.vacation_readonly')` ("Vacation mode can only be set on the Toon itself" / "De vakantiestand kan alleen op de Toon zelf worden ingesteld") before any request. **UX consequence recorded**: `temperature_state` is a setable `picker`, and the SDK has no per-value read-only flag, so "Vacation" *is* selectable on the tile and selecting it shows that message; Homey leaves the stored value unchanged because the listener rejects ([D] Device.html; HW-04 verifies the toast and that the picker returns to the current state). Setting vacation from Homey (`state=8&temperatureState=4`, M/L confidence) is not in 2.0.0.
* **Burner**: new custom enum capability `burner_state` defined in `.homeycompose/capabilities/burner_state.json` as `{"type": "enum", "title": {"en": "Burner", "nl": "Brander"}, "getable": true, "setable": false, "uiComponent": "sensor", "insights": false, "values": [off|heating|hot_water|preheating with en/nl titles]}` (<- `burnerInfo` `0|1|2|3`, one table in `lib/toon/parse.js`), in `CORE`, added to legacy devices by the migration, no extra request; cards `burner_state_changed_to` and `burner_state_is` (ADR-0009). `insights: false` because Homey Insights logs number and boolean capabilities; the enum changes are available through the trigger card. `alarm_water.hotwater` (`burnerInfo === 2`) keeps id, title and semantics.
* **Plain `meter_power`**: never added (Homey Energy would start counting it, C-CAP-3) and **never written** by 2.0.0. Era-0 devices keep the capability with its last value and its Insights log (that is what users keep); `parsePower` has no `dayUsage` branch, because a daily value in a cumulative slot violates B-8 and the counter policy below would otherwise pin it at the day's maximum. Changelog line: "the legacy total power meter on devices paired with version 0.0.1 is frozen; use the peak and off-peak meters".
* **Counter-decrease policy** (replaces the blanket monotonic guard; `04` B-8 asks only that a *failed or partial payload* never decreases a counter): for `meter_power.peak`, `meter_power.offPeak`, `meter_gas` and `meter_water.total`, a value that is `0`, non-finite or `"NaN"` is rejected unconditionally; a finite non-zero value **lower** than the stored value is held back and counted; when three consecutive cycles each deliver such a lower value, the latest is accepted and one info line is logged ("meter counter decreased for 3 cycles; accepting new baseline"); any reading >= the stored value resets the count. The count lives in memory (a restart restarts the three cycles). `meter_water.today` is exempt (it resets at midnight by design) and no `measure_*` capability is touched by the policy. The README notes that Homey Energy shows one odd interval after a meter replacement.
* **Precision**: `meter_power.peak/offPeak` and `meter_gas` use 3 decimals; single-tariff fallback kept (peak from the combined node when the nt node is `"NaN"`, off-peak untouched). The one-time step is noted in the changelog. **`target_temperature` is rounded to the capability step** in `parseThermostat` (`Math.round(v * 2) / 2`: `1975` -> 20.0, `1974` -> 19.5); `measure_temperature` stays at 0.1. The strict fake rejects an off-step `target_temperature` so the rounding cannot be dropped silently; whether Homey itself rejects off-step values is HW-03.
* **Discovery**: `discoverMeters(json)` tries the legacy keys `dev_2.1/2.4/2.6/2.2` first (continuity for dev_2 Toons and the users who patched `dev_4.x`), then exact `type` strings from `METER_RULES` fill the gaps; two candidates for one role -> no write and one info line per device start naming the candidates. Parsers use `Object.hasOwn` and `typeof x === 'object' && x !== null`, never call methods on payload objects, and never `Object.assign`/spread a payload into long-lived state. The table is seeded from 03 §4.4 (M confidence) and may be edited only after real dumps (HW-02).
* Not in 2.0.0: instantaneous gas (FR-29), program state read-back (FR-15), manual node override (FR-23).

## Consequences

* No `undefined`/`NaN`/`0` ever reaches a capability (C-CAP-6); a failed or partial payload never decreases a counter (B-8); a real counter reset is accepted after three confirmations instead of freezing the capability forever.
* Mapping tables are single points of change for the hardware captures (HW-02, HW-04, HW-08).
* Rejected: a boolean "burner on" capability (loses hot water and pre-heat); net-signed `measure_power` (FR-27 WONT); computing a cumulative `meter_power` from day usage (wrong semantics); keeping the baseline's `dayUsage` write "for compatibility" (a harmful write has no compat value; the capability is kept); ignoring every decrease (silent flat-line after a meter replacement).
