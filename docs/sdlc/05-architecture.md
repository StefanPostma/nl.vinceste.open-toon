## 1. Verdict

**Base: candidate C (declarative feature registry), amended.** Grafted from B: injected timers in the HTTP client, write priority on the per-device lane (rev 2: priority in the queue, never an abort of an in-flight request, section 5), `newSettings`-only `onSettings` (rev 2: `planSettingsChange(newSettings, changedKeys)`), the layering test, the strict fake-Homey conventions and the in-process `fetch` adapter (rev 2: contract in ADR-0013). Grafted from A: the small file budget, read-only status labels (`last_update`, `last_problem`), the one-time timeline hint for migrated devices, the `burner_state_changed_to` card id and the "no network before the marker" migration. Rejected: A's hand-maintained flat `app.json` (violates HS-10/11 and the owner's "latest standards" intent), B's four-layer tree with a composition root on `this.homey.app` and its `ClientPool` (weight without a requirement behind it), B's `burner_state_changed` id (collides with Homey's auto-run of `<custom capability>_changed`, HS-42).

Why C and not "A plus Compose": the owner's second intent is a *mechanism* ("a feature that you can enable if wanted"), the requirements already name a second opt-in feature for the same release (FR-25 power export, OQ-06 recommends opt-in) and a third that must "follow the opt-in pattern" (FR-33). A design that writes the lifecycle (setting, capabilities, poll group, probe, status, legacy default, pairing checkbox, guarded cards, trigger rules) once as data, and proves with a synthetic fourth feature that the engine needs no edit, is the smallest design that is correct for all three. A would re-open `device.js` for every feature; B pays for the same outcome with 35 files.

## 3. Decision 1 - Module and file layout, Homey Compose (ADR-0002)

**Decision.** Adopt Homey Compose (`homey app compose` once as a mechanical step, then hand-maintained compose sources; HS-10..12). What the command writes and what is done by hand (the `settings` split, `burner_state.json`, `vacation`) is listed in ADR-0002 step 1; **`.homeycompose/locales/` is never created**, because Compose would then deep-merge it into the hand-maintained `/locales/*.json` on every validate/build (F-09; L3 asserts the directory is absent, CI diffs `locales/`). The generated `app.json` is committed (HS-11 note: the scaffold's `.gitignore` does not exclude it) so plain-Node tests read the manifest without the CLI; CI fails on `git diff --exit-code app.json locales/` after `homey app validate`. Water capabilities leave the driver's `capabilities` list (FR-51 AC1) but their titles stay in `capabilitiesOptions` (the superset, 02 W9; the validator types `capabilitiesOptions` as a plain object and checks only option values - candidate C read this in `node-homey-lib` `develop` `lib/App/index.js` ~L406-460, the standards review confirmed it; **re-verify once by running the validator in CI**). **This is a deliberate deviation from `04` C-CAP-1 and is recorded as a contract exception in ADR-0017** (issue 1): CT-01 compares baseline capability ids against `capabilities ∪ keys(capabilitiesOptions) ∪ FEATURES[*].capabilities`, requires the three ids to be listed in `test/fixtures/contract-exceptions.json` with the ADR reference (FR-76 AC2), and now also compares the `device` argument filter string (R-33, which the earlier text claimed and Appendix A did not check).

## 4. Decision 2 - HTTP client replacing `homey-wifidriver` and `request-promise-native` (ADR-0003)

**Decision.** `lib/toon/client.js` wraps the Node 22 built-in `fetch` (HS-02: "the preferred approach for new code"). No runtime dependency. Signature:

```js
new ToonClient({ host, fetch, timers: { setTimeout, clearTimeout }, timeoutMs = 5000, maxBytes = 2 * 1024 * 1024 })
client.get(endpoint /* {path, query} */, { signal, priority }) -> Promise<object>
```

* **Address first** (R-11): `normalizeAddress(input)` never throws - non-strings -> `{ok:false}`, `new URL` wrapped in `try/catch` (`:99999`, bare IPv6 throw), then `protocol http:`, empty `username`/`password`/`search`/`hash`, `pathname '/'`; `https://` and IPv6 (bracketed or bare) are rejected with their own localized reasons (no evidence of a Toon on IPv6; ADR-0003). L0 table adds `[fe80::1]`, `fe80::1`, `https://1.2.3.4`, `:99999`, `12`, `null`, `{}`.
* URL built with `new URL('http://' + host)` + `url.pathname = path` + `url.searchParams.set(k, v)`; never string concatenation (NFR-04 AC1; `device.js:94,122,151,177,209,247,272,297` concatenate today). Only `http:`.
* `fetch(url, { redirect: 'manual', headers: { 'Accept-Encoding': 'identity', 'Connection': 'close' }, signal })`. Any 3xx -> `ToonError('redirect')` (NFR-04 AC2). `Accept-Encoding: identity` follows the long-running HA clients (03 T4, M confidence; HW-H4 tests both). **`Connection: close`** (F-08): undici pools sockets per origin; the Toon's embedded server idle policy is unknown, and a socket it closed between a poll and the `refreshSoon(1500)` write would surface as `fetch failed`/`ECONNRESET` = a counted core failure. At >= 10 s cadence pooling buys nothing. Verified on Node 25.9 that the header reaches the server; L1 repeats it on Node 22; HW item next to H4; mock mode `idle-close`.
* **Timeout by injected timers**, not `AbortSignal.timeout`: a **per-request** `AbortController` aborted from `timers.setTimeout(..., timeoutMs)`; the device's epoch signal is attached through an `abort` listener added before the request and removed in `finally` (R-10: no dependent-signal accumulation on the long-lived epoch signal, nothing to prove about `AbortSignal.any` release on Node 22). Reason: fake-clock scenarios (availability after timeouts, back-off) become deterministic and no global timer exists in `lib/` (lint `homey-app/global-timers`, HS-06). Grafted from B.
* **Resource hygiene on every path** (R-10): `clearTimeout` in `finally`; `await res.body?.cancel()` on 3xx, non-2xx, `too_large`, `bad_body` (undici otherwise keeps the socket reserved; a Toon answering 500 on `getDevices.json` for hours would leak one socket per cycle). L1 asserts `server.getConnections() <= 1` after 50 error responses and a stable `process.getActiveResourcesInfo()`.
* Body read as a stream with a byte counter; > `maxBytes` -> abort + `ToonError('too_large')` (NFR-04 AC3). Then `JSON.parse(text)`: the Toon answers `Content-Type: text/javascript` (03 T3), so `res.json()` is not trusted. Non-object -> `bad_body`. `result === 'error'` -> `toon_error`.
* `ToonError extends Error { kind, status?, cause? }`, `kind` in `timeout | network | http | redirect | too_large | bad_body | toon_error | aborted | config`. `isNotFound(e)` = `http` + 404. `aborted` from a **poll cycle** is never logged, counted or shown; `aborted` on a **user-initiated task** (card, capability set, `onSettings`) rejects with the localized `error.aborted` text (R-06, section 5 Cleanup). **No user text in the client**; `lib/messages.js` maps every `kind` -> locale key (`error.timeout`, `error.network`, `error.http` with `__status__`, `error.bad_body`, `error.toon_error`, `error.aborted`, `error.address_https`, `error.address_ipv6`) in en + nl (NFR-16, FR-73 AC2).
* **Payload hygiene** (R-12): parsers use `Object.hasOwn` and `typeof x === 'object' && x !== null`, never call methods on payload objects (the baseline's `payload['dev_2.4'].hasOwnProperty`, `device.js:381,395`, throws on `null` and on `{"hasOwnProperty": 1}`), and never `Object.assign`/spread a payload into long-lived state (`JSON.parse` yields own `__proto__` keys). Fixtures: `{"dev_2.4": null}`, `{"dev_2.4": {"hasOwnProperty": 1}}`, `{"__proto__": {"polluted": 1}}`, `{"water": []}`, `{"powerUsage": "460"}`.
* **No retries in the client.** Retry/back-off policy belongs to the poller (section 5). `/water.html` is **not** a client method: `lib/features/toonwater.js` owns the endpoint object and calls `client.get(endpoint)` (FR-60 AC3).

**Verified locally (Node 25.9, to be re-run on Node 22 in CI):** `redirect:'manual'` yields the 3xx response itself; `Accept-Encoding: identity` is sent; `JSON.parse(await res.text())` works for `text/javascript`; the abort reason surfaces as the rejection (candidates A and B ran these; the standards and robustness reviews repeated them); rev 2: `Connection: close` is passed through and `body.cancel()` returns the socket (architect, 2026-11-12). **[HW]** H4 (`identity` vs `gzip`, keep-alive vs `Connection: close` on a real Toon), T3 content type of `/water.html`.

**Rejected.** `node:http` with a `>=5.0.0` floor (CD-5 option 2): keeps Node 12/16 runtimes alive and forbids `fetch`, `?.`, `AbortSignal.any`; the audit's two-release plan (v1.1.0 hotfix at `>=5.0.0`) doubles the work for users nobody has evidence of. `undici`/`node-fetch`/`axios`: a dependency for nothing (03 J16). Retries inside the client: hides load from the poller's budget (NFR-03).

## 5. Decision 3 - Poll scheduler, intervals, back-off, availability, in-flight guards, cleanup (ADR-0005)

**Scheduler.** One self-rescheduling `this.homey.setTimeout` chain per device (HS-22; never `setInterval`), re-armed in `finally`. One in-flight cycle at most (`_inflight` promise). First cycle 1 s + `random(0..2000)` ms after `onInit` returns (spreads several Toons; FR-80 AC2 "within 5 s").

**Lane (per-device priority queue; one request in flight; never aborts for priority).** All Toon traffic of a device goes through one `Lane`: poll cycles, "Update" cards, writes, probes. `lane.run(fn, { kind: 'write' | 'refresh' | 'poll' })` orders waiting tasks `write` > `refresh` > `poll`, FIFO within a class, and runs **exactly one request at a time**. **Rev 2 (R-01): a request in flight is never abandoned to make room for another request to the same host.** The first draft let a write abort an in-flight poll GET; an abort only closes the Homey-side socket while the Toon keeps executing the GET, so the Toon would have had two requests in progress and NFR-03 AC1 ("never two concurrent requests to one Toon") would have been false in exactly the section that claimed it, unobservably so with an in-process `fetch` double that forgets aborted requests. Instead the **cycle takes the lane per group request and yields between groups**: a write or card that arrives during a poll request starts when that request settles (<= 5 s) and before the next group. Aborts exist only for teardown and address change (epoch `gen++`), after which this device sends nothing more to that host. NFR-03 AC1 therefore holds per device as written and is **measured** by the mock's server-side `maxConcurrent()` (ADR-0013). **NFR-08 AC2 is amended by ADR-0005**: a Flow action or capability set is *started* at the latest when the in-flight request settles and *settles* within its own 5 s timeout: <= 6 s when the Toon answers polls within 1 s (the normal case), <= 10 s under a pending poll timeout; L2 asserts both bounds. **Refresh coalescing (R-15, B-3, FR-74 AC3):** at most one *pending* refresh per group; later refreshes for the same group join it and share its (fresh) result; a refresh for a group whose poll request is in flight joins that request. Ten legacy timer Flows firing `update_status` together cost one targeted cycle (CT-08). **Rejected:** B's per-address `ClientPool` shared across devices (two devices on one Toon is a test-only pattern; a cross-device mutex is the likeliest place for a subtle bug and has no requirement behind it). **Consequence accepted and documented (R-19):** NFR-03 AC3 ("one in flight per Toon") holds **per device**; two devices paired on the same Toon make two lanes and up to two concurrent requests at that Toon; the README says so, and HW-10 notes the doubled load when the fixture-device pattern of `04` §10.2 is used.

**Cycle.** `activeGroups(featureState)` in declared order: `thermostat` (`critical:true`) -> `power` -> `meters` -> feature groups (`water` when enabled). Each group has its own try/catch for `http`, `bad_body`, `toon_error`, `redirect`, `too_large`: one endpoint failing never skips the others (FR-80 AC4). **Rev 2 (R-02): if the critical group fails with kind `timeout` or `network`, the cycle ends after that group** - the host is down, and requesting power and meters would hold the lane for 15-20 s per cycle, triple the Toon-side timeouts and make every queued card wait. A group may declare `every: n` (run every n-th cycle; HW-10 may want `meters` at 2), `absentOn404: {backoffMs}` and the water escalation (section 6.6). Group results are `{values, notes}`; `applyValues` (section 8) is the single writer. L2: "Toon unreachable 10 min" asserts one request per cycle; "meters returns 500" asserts thermostat and power still applied.

**Interval and back-off.** `intervalMs = clamp(Number(poll_interval) || 30, 10, 3600) * 1000` (FR-83, FR-112; defaults resolved on read, never persisted, U3/R-29). After consecutive **core** failures `n`: delay = `interval` for n = 1, 2; then `min(interval * 2^(n-2), max(300e3, interval))` (FR-81 AC3, NFR-03 AC2; rev 2 R-07: the first draft's `min(..., 300 s)` *shortened* a 3600 s interval to 300 s while the Toon was down, a 12x rate increase). Reset on the first successful critical group. A request aborted by the epoch **neither increments nor resets** the counter (R-15). Water back-off: section 6.6.

**Availability.** A cycle fails only when the `thermostat` group fails (timeout, network, HTTP >= 500, bad body, redirect, too large). **Rev 2 (R-17):** `unavailable = (failures >= 3 && elapsed >= 90 s) || (failures >= 2 && elapsed >= 15 min)`, `elapsed = now - firstFailureAt`, four named constants tuned in HW-10; a pure cycle count made a 30 s hiccup at a 10 s interval flip the device while a 3600 s interval stayed "available" for three hours. **FR-81 AC1 is amended by ADR-0005** accordingly. `setUnavailable(this.homey.__('offline'))` on the transition (R-10 accepted: Homey then blocks Flow actions). First success -> `setAvailable()`. Values are never cleared (FR-81 AC4, C-CAP-6). Polling continues while unavailable with the back-off above, so recovery needs no Flow and no restart (FR-81 AC3). The Toon's nightly reboot (03 T6, single source) can flip availability once a night at defaults: accepted. L0 table over intervals 10/30/3600.

**Guards.** `gen` (bumped on address change and teardown), per-feature `featureGen` (bumped on every toggle), `writeSeq` (a thermostat response requested before a write is dropped, FR-16 AC3). Every response is checked against `_stopped`, `gen`, the group's `featureGen` and `hasCapability(id)` **before** `setCapabilityValue` (FR-53 AC3, FR-82 AC2, FR-84 AC2). A dropped response is logged at debug, never error.

**Writes.** `target_temperature`: validate finite and 6..30, round to 0.5, **latest-wins single flight** (one in flight + one trailing; a slider drag sends <= 2 requests, FR-16 AC1), value sent as `Math.round(deg * 100)` (integer, FR-11 AC1). **Rev 2 (R-04): no optimistic `setCapabilityValue`** - it was a second writer door (NFR-01 AC2), stored an unconfirmed value that stayed on the tile while the Toon was unreachable, and made the system `target_temperature_changed` fire twice on a failed write. `04` B-5 is amended by ADR-0005 (the baseline needed it only because `request-promise-native` had no timeout, `device.js:243`). The listener awaits the Toon; Homey stores the value when the listener resolves and leaves it unchanged when it rejects ([D] Device.html; the fake models this; HW-03/HW-13 confirm the tile). After a successful write: `writeSeq++`, `refreshSoon(['thermostat'], 1500)` (FR-16 AC2). Failure rejects with a localized message and schedules an immediate thermostat refresh (FR-11 AC3). L2 "write fails" asserts the stored value equals the Toon's after refresh and no change event for the failed write.

**Cleanup.** `onUninit` and `onDeleted` call one idempotent `_teardown()`: `_stopped = true`, `gen++`, abort the epoch `AbortController`, `clearTimeout`, and **rev 2 (R-06): reject every task still queued in the lane or the serial queue with `ToonError('aborted')`** so no Flow hangs until Homey's own timeout. `toUserMessage` maps `aborted` to `error.aborted` ("The request was cancelled because the device was removed or its address changed" / nl in ADR-0005); "never shown" applies to poll results only. Every multi-step serial task (toggle, migration) checks `_stopped` before each Homey call, because `addCapability`/`removeCapability`/`setSettings` throw on a deleted device. Never throws (FR-84 AC3; baseline `device.js:488-491` throws). `onDeleted` also `unsetWarning().catch(...)`. Nothing runs after teardown (FR-84 AC1). L2: "delete while a card is queued" asserts the card rejects with the localized text in the same tick and zero unhandled rejections; "address change mid-write" asserts the write rejects with the `aborted` text and the next cycle uses the new host.

**Never-rejects rule (R-09).** `this.homey.setTimeout(() => this._cycle(), ms)` returns a promise from an arrow, which `no-floating-promises` does not flag, so a rejecting `_cycle` would be an unhandled rejection. Every entry point invoked by a timer or by Homey without an awaiting caller (`_cycle`, `refreshSoon`, the deferred status write, the FR-62 notification, warning and availability updates) is `async`, has a top-level `try/catch` that logs, and never rejects. L3 greps that every `this.homey.setTimeout(` callback calls a function on the never-rejects allow-list; the harness counters (NFR-01 AC1) remain the executable proof.

**Logging (NFR-09).** State transitions are logged once on entry and once on exit (offline/online, water found/not found); a healthy cycle logs at most one short line; raw payloads only when `debugPayloads` is true. **Rev 2 (F-04):** a Homey app's process environment is set by the runtime, so `process.env.OPEN_TOON_DEBUG` was unreachable on an installed build; `debugPayloads = process.env.DEBUG === '1' || this.homey.env.OPEN_TOON_DEBUG === '1'`, computed once in `App#onInit` (the first is set by `homey app run`, the second by an uncommitted `env.json` `{"OPEN_TOON_DEBUG": "1"}` present at `homey app install` time, [D] app.md). Trade-off recorded in ADR-0005: no runtime toggle on an installed build (a device/app setting would be the only SDK option and is rejected as UI clutter); HW-10 installs with `env.json` present.

## 6. Decision 4 - THE TOONWATER OPT-IN, end to end (ADR-0006, ADR-0007)

### 6.1 Definitions (from 04 §7.1, which corrects 02 W5/W6)

*ToonWater* = the Toon-side add-on serving `/water.html` (03 §5). The **water group** = capabilities `measure_water`, `meter_water.today`, `meter_water.total`, action `update_water`, app trigger `measure_water_changed`. **Not** in the group: `alarm_water.hotwater`, `hotwater_dispensing`, `alarm_water_changed` (fed by `burnerInfo === 2`, `device.js:475-477`): they live in `core.js` and are never guarded, filtered, added or removed by the toggle (FR-31, R-36).

### 6.5 Toggling at run time, including races with an in-flight poll

Everything below runs inside the device's **serial queue** (one promise chain shared by migration, `onSettings`, toggles; FR-52 AC4). `onSettings({ oldSettings, newSettings, changedKeys })` never calls `getSetting` (stored values are still the old ones until it resolves). **Rev 2 (R-24, R-16):** `planSettingsChange(newSettings, changedKeys)` is pure, acts **only on keys in `changedKeys`**, normalises before comparing (a `poll_interval` saved as a string, an address with extra whitespace, or the status `label` keys present in `newSettings` must not bump `gen`), and returns `{ errors, addressChanged, startPoller, intervalChanged, toggles[] }`; `startPoller` is true when the stored address was invalid (`0.0.0.0`/empty, device unavailable, no poller) and the new one is valid - the poller is then started and its first success calls `setAvailable()` (L2 "legacy `0.0.0.0` then valid address"). Validation errors are thrown as localized `Error`s first (FR-82 AC1, FR-83 AC1). **Every step below re-checks `_stopped` before a Homey call** (R-06: the device may be deleted mid-save).

**Off -> On.**
1. `featureGen.toonwater++`; clear `absentUntil` and the water failure count.
2. `reconcile`: `addCapability` x3 (each guarded by `hasCapability`), **wrapped (issue 9)**: if one of them throws (Core refusing an id not in `driver.capabilities` - unverified - or a transient error), the ids added in this same step are removed again (guarded) and the error is rethrown, so `onSettings` rejects, Homey keeps `toonwater_enabled = false`, and no stray, unpolled water capability with a system card and tag is left on the device (M-5 would otherwise keep it forever). Then **options reconciliation (F-06, issue 4)**: `setCapabilityOptions(id, driver.manifest.capabilitiesOptions[id])` only when `getCapabilityOptions(id)` deep-differs from it (C-CAP-4 kept; three "expensive" calls skipped in the common case; U2 **[HW]** HW-03). L2 "second `addCapability` rejects".
3. `probe(client)` with the (possibly new) address, **`kind: 'write'` priority and a 3 s budget** (R-03, F-06; the same budget pairing uses): the probe no longer queues behind a 15-20 s cycle, so the network part of `onSettings` is <= 5 s (one in-flight request settling) + 3 s = 8 s worst case and typically well under 1 s. A probe cancelled by teardown or a later address change classifies as `unreachable`. Homey shows the save toast only after `onSettings` settles and its UI timeout is unknown, so "save duration with ToonWater enabled on a slow Toon" is added to HW-13. L2 "slow poll in flight + save with toggle" asserts `onSettings` resolves within 8 s of fake time with the FR-59 texts.
4. Status + message: `detected` -> "ToonWater found..."; `not_found` -> capabilities **stay** (D-4), `setWarning` (the user decided, so the warning applies), message "not found..."; `unreachable` -> message "could not be reached" (FR-55 AC5), status "Toon not reachable"; `unexpected` -> status "Unexpected response". `store.toonwaterDecidedBy = 'user'`; delete `store.waterFirst404At`.
5. The water group joins `activeGroups`; `refreshSoon(['water'], 0)` is **scheduled, not awaited**, after the return value is produced, so first values land within 10 s (FR-52 AC1) without lengthening the save.

**On -> Off.**
1. `featureGen.toonwater++` **first**. The in-flight water request, if any, is **not** aborted (rev 2, R-01: an abort would not stop the Toon and would free the lane for a second request); its response carries the old gen and is dropped silently before `hasCapability` is even consulted (FR-53 AC3: no `Invalid Capability`, no error-level line).
2. The water group leaves `activeGroups` (the running cycle re-reads the snapshot only at its next group boundary; the gen check covers the rest). Zero `/water.html` requests afterwards (FR-53 AC2).
3. `removeCapability` x3 (guarded), `unsetWarning()`, status "Off", `store.toonwaterDecidedBy = 'user'`, delete `store.waterFirst404At`, return the amended FR-59 "turned off ... Flows that used them need to be updated and their Insights history may be lost" message (FR-54 AC3, issue 3).
4. Only the three water capabilities are touched; `alarm_water.hotwater`, burner, power, gas, their values and options are untouched (FR-60 AC1).

**Rapid tick/untick/tick (FR-52 AC4).** The queue serialises the three saves; each step re-reads `hasCapability`, so no duplicate add, no invalid remove; the final state equals the last save.

**Toggle during an address change.** `planSettingsChange` orders: address first (`gen++`, abort epoch, new client, reset back-offs, `startPoller` if the device had no poller), then toggles (probe uses the new client). If ToonWater is enabled and only the address changed, it is re-probed and `absentUntil` cleared (FR-82 AC2). The FR-82 scenario also asserts "address fixed -> no stale warning" (F-10).

**Transient failure while on (404, timeout, reboot).** No change, never auto-off (D-3). Warning + back-off only.

### 6.6 Detection and user feedback

One `probe` code path serves pairing, enable, address change and the first poll after enable: `GET /water.html` -> 200 + `result:"ok"` + object `water` = `detected`; HTTP 404 = `not_found` (03 T8, M confidence: **[HW]** HW-07 records the real status without the add-on and after a reboot before the first sensor poll); timeout/refused/DNS = `unreachable` (availability stays with the thermostat); other 200, 403, 500 = `unexpected`/`http`. While polling, the water group itself is the detector: on entering `not_found` log one info line, set the warning under the ADR-0018 rule, back off 15 min; on leaving, log once, clear the warning, resume per-cycle polling (FR-55 AC2, FR-57 AC2, NFR-09). A persistent 404 never creates an error-level line and makes at most 1 + 96 requests per 24 h (FR-55 AC4). **Rev 2 (issue 8, R-23): the load bound no longer depends on T8 being right.** Any other non-success water result (200+HTML, 403, 500, garbage, timeout) backs off 5 min for the first three consecutive failures and 15 min from the fourth on (`failEscalateAfter: 3`), status text per kind, so a Toon whose web server answers 200+HTML for a missing page costs <= 100 `/water.html` requests per 24 h instead of ~288 with "Unexpected response" on every P1 tile; HW-07 can then change wording, not load. FR-55 AC4 is asserted as <= 97 for 404 and <= 100 for the other kinds. The mock gains water modes `html-200`, `403`, `500`; if hardware shows a missing add-on answers 200 + `text/html`, `probe` maps `unexpected` with `text/html` to `not_found` (one line).

**FR-62 hint (rev 2, issue 6 / R-14 / R-22, ADR-0018).** For a device whose ToonWater state was decided **by migration** and whose every water attempt returned 404 for 24 h, one timeline notification (`this.homey.notifications.createNotification({ excerpt })`, en + nl; no manifest permission needed, [R] ManagerNotifications.html) says ToonWater is on for this Toon but not found and where to switch it off. **Restart-safe:** the water group writes `store.waterFirst404At` on entering `not_found` (if absent) and deletes it on any valid payload or user toggle; the hint fires when `store.toonwaterDecidedBy === 'migration' && now - waterFirst404At >= 24 h && !store.waterHintSent`; `waterHintSent` is written **only after** `createNotification` resolved, a rejection is logged and retried at the next water attempt. Nothing is sent for user-decided devices or when the device was disabled/deleted in the meantime (FR-62 AC1-3). L2: a device re-instantiated over the same fake store at 12 h still fires at 24 h; `createNotification` rejecting once yields exactly one notification.

### 6.7 Flow cards (ADR-0007: CD-1 decided as option C of 04 §7.3)

Facts: manifest cards are static; the `capabilities=` card filter "does not update" on `addCapability`/`removeCapability` ([D] flow.md, HS-44); `deprecated` is global (HS-46); capability-generated **system** cards and Flow tags follow the device's current capability list ([D]); sub-capabilities get no system cards (HS-35).

**Decision.** `update_water` and the app trigger `measure_water_changed` get `"deprecated": true` (hidden from "Add card", still run; FR-71/FR-75 ask for exactly this). **No `capabilities=` filter is added** to any card: it is documented not to follow runtime toggles, so it would hide the cards for precisely the users who enable ToonWater later (R-06). What a user sees for water is what Homey generates from the capability: the system trigger `measure_water_changed` and the three tags appear when enabled and vanish when disabled. "Refresh now" is `update_status` ("Update now" / "Update nu", refreshes every enabled group). Run listeners stay registered and are safe on any device. **`update_water` with ToonWater off (rev 2, issue 2, ADR-0018):** the baseline offered the card to every device (`app.json:513-525`) and `getWater()` swallowed every error (`device.js:171-190`), so under HEAD it silently *resolved* on devices without water; `04` R-08 accepted a rejection on the premise that the off state is "reachable only after a deliberate user toggle", which is false for eras 0/1, where the migration itself sets off. Therefore: when `store.toonwaterDecidedBy === 'migration'` the card **resolves as a no-op** (no request, one debug line), so a legacy #5/#25 Flow that chained it keeps running; after a user toggle it rejects with the FR-59 text "ToonWater is not enabled for this device" and sends nothing (FR-54 AC2 amended to the user-decided case; fallback CD-2 `onDisabled: 'noop'` for everyone remains one word in the feature object). CT-04 gains "era-1 fixture: `update_water` resolves, zero `/water.html` requests". The app `measure_water_changed` trigger fires only from changes the writer produced, so it cannot fire while off.

**What happens to Flows when ToonWater is disabled.** Homey documents that `removeCapability` makes "any Flow that depends on this capability ... broken" ([D] Device.html) and the Homey-side Insights history of the three logs may be deleted (`04` U5). The app edits no Flow (FR-54 AC3; OQ-13: no SDK API lists Flows per capability). **The hint, the save message and the README say both** (rev 2, issue 3: the first draft mentioned Flows only, although `04` R-04 names exactly this text as the mitigation for the one path where the opt-in can destroy user data). Re-enable restores the **same ids**, so a Flow built on them can resolve again (FR-54 AC4); whether Homey heals a broken Flow automatically and whether Insights history survives are **[HW]** HW-05/HW-08 (04) and are written into the README "what happens to my Flows" section (FR-54 AC5, FR-122); the Insights clause is dropped if the history survives. This deviates from FR-52 AC5 / FR-53 AC5 / FR-54 AC1 as written (they assumed a filter); the requirement intent ("no water cards when off, cards when on") is met through Homey's own mechanism, and FR-54 AC1 is amended to "declared, deprecated, no filter" by ADR-0007.

### 6.8 Provenance (NFR-11)

`lib/features/toonwater.js` is written from the interface description in 03 §5.3 (URL, JSON fields, units) and reuses the semantics of this repo's GPL-3.0 PR #21 (`f705a70`, `device.js:410-424`: `/1000` for `value` and `total`, `flow` unscaled). The file header records this. No source of `oepi-loepi/*` is read, quoted or paraphrased for it. The UI uses the name "ToonWater" per FR-59; the owner is asked to confirm the name use with its author (03 §10 items 1 and 13).

## 7. Decision 5 - Pairing on `PairSession` (ADR-0008)

`Driver#onPair(session)` registers two handlers (HS-50):

* `testConnection({ address })`: `normalizeAddress` (localized error on empty/invalid, no request; FR-01 AC3, FR-03) -> `client.get(thermostatInfo)` with 5 s timeout -> requires `currentTemp` and `currentSetpoint`, else `error.not_toon` ("does not look like an open Toon", FR-02 AC3); 404/500 -> `error.http` with the status (FR-02 AC4); timeout -> `error.timeout` within 6 s (FR-02 AC2). Then every optional feature's `probe` (water: own 3 s budget; a probe failure never fails the test, FR-61 AC3). Returns `{ host, readings: { currentTemp, currentSetpoint, programState, activeState }, features: { toonwater: 'detected' | 'not_found' | 'unknown' } }`.
* Both handlers **`typeof`-check every field first** (rev 2, R-11: the view can send non-strings; `id.trim()` on a number would throw) and reject with a localized error otherwise.

## 8. Decision 6 - Flow trigger firing and the deprecation plan (ADR-0009)

**Firing.** `Driver#onInit` fetches each `getDeviceTriggerCard(id)` once (HS-41). `applyValues` returns `Change[] { id, prev, next }`; the engine evaluates the feature `rules` and calls `card.trigger(device, tokens, state).catch(this.error)` (FR-70 AC3). A trigger fires **only** when `prev !== null && prev !== next` (FR-70 AC2/AC4: the first value ever fires nothing; after a restart Homey's stored value is `prev`, so a change that happened while the app was down fires once).

| Card | Policy |
|---|---|
| `meter_gas_changed` | fire; token `meter_gas` (m3, 3 decimals); **deprecated** (duplicates the system card, FR-71) |
| `meter_power_changed` | fire once per cycle when peak or off-peak changed; token `meter_power` = peak + offPeak in kWh, 3 decimals; token **title** "kWh" (was "Wh", `app.json:212`, title-only fix); sum only (OQ-09: extra tokens are an additive later option) |
| `measure_water_changed` (app) | fire while ToonWater is on; **deprecated** |
| `alarm_water_changed` | fire on boolean change; token `alarm_water.hotwater` (dot kept, R-16) |
| `temperature_state_changed` | **not fired by app code** (`source: 'homey'` in the rule table): Homey auto-runs `<custom capability>_changed` on `setCapabilityValue` (HS-42, R-12, CD-4). Amends FR-70 AC1 for this one card. **[HW]** HW-06 (04): if Homey does not fire it, flip the one-word policy to `'app'` |
| `burner_state_changed_to` (new) | fire on `burner_state` change with `state` dropdown `any|off|heating|hot_water|preheating`; run listener compares `args.state`. The id deliberately avoids `burner_state_changed`, which Homey auto-runs for the custom enum and could call an argument-bearing listener without state (FR-32 id amended, OQ-11) |

**Conditions.** `temperature_state_is` (+ `vacation` in the dropdown, baseline default `comfort`) and the new `burner_state_is` compare `normalizeDropdown(arg)` (string or `{id}`, U7) with the capability value and return strict booleans (`null` -> `false`, FR-72). `hotwater_dispensing` returns `=== true`.

**Actions.** `set_temperature_state`, `enable_program`, `disable_program` await the Toon and check `result`, else reject with `toUserMessage` (FR-73; B-6). `resume_program`: `undefined` -> `yes` (R-18). `update_status` -> "Update now" / "Update nu", refreshes every enabled group, rejects only if `thermostat` failed; `update_powerusage`, `update_metertotals`, `update_water` refresh their own group and reject only if that group failed (water 404 excepted) (B-2, R-37, R-09 changelog line). Rev 2: concurrent `update_*` cards for one group **coalesce** into one request (section 5, B-3); `update_water` while off is a no-op on a migration-decided device and a localized rejection after a user toggle (ADR-0018); a card still queued at teardown or address change rejects with the `aborted` text, never hangs (R-06); no action or capability listener writes a capability optimistically (R-04). Dropdown values carry both `title` and `label` until HW-10 (04) (R-17, CD-6).

**Deprecated (`deprecated: true`, listeners kept):** `meter_gas_changed`, `measure_water_changed`, `update_powerusage`, `update_metertotals`, `update_water`. One-way door: the contract check (CT-01) fails on un-deprecation. `update_status` stays visible.

**Manifest fixes in the same move (validator blockers and text, all non-contract):** `[[resume_program]]` added to `set_temperature_state.titleFormatted` en + nl (`app.json:388-391`; fails `debug` level today, HS-17); nl `!{{is|is niet}}` (`:314`); `title` on every dropdown arg (needed at `verified`, HS-45); no parentheses/device names in titles (HS-40).

**Changelog lines required (R-09, R-11, R-13, R-20):** update cards now fail when the Toon is unreachable; dormant triggers start firing; gas and kWh gain three decimals; `vacation` state added; ToonWater is now a per-device setting.

## 11. Decision 9 - Compatibility floor and version number (ADR-0004)

`compatibility: ">=12.9.0"`, `version: "2.0.0"`, `platforms: ["local"]` (app and driver), driver `connectivity: ["lan"]`, `sdk: 3`.

Rationale: from Homey v12.9.0 every platform runs apps on Node 22 (HS-01), which gives built-in `fetch`, `AbortSignal.any`, `node:test` on the dev side, and the energy manifest keys (`>=12.3.0`) should FR-90 ever ship (HS-14). `1.0.0` is shared by three different builds (eras 1-3, 04 rule 2), so the next version must be `>= 2.0.0` and Homey never downgrades (R-31). Consequence stated in the release note: Homeys on firmware below 12.9.0 keep the old build (R-26). Rejected: `>=5.0.0` + `node:http` + Node-12-safe syntax (two runtimes to test, no `fetch`, no evidence of any user on old firmware); a separate v1.1.0 "installable again" hotfix release (audit §4) is **not** made; a one-line patched baseline (`[[resume_program]]`) exists only as a **test artefact** for HW-12 (OQ-15: tag it `baseline-patched-for-hw12`, never publish it).
